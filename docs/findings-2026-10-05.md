# Front Door Conditional Requests: Measured Results

**Date:** 5 October 2026

**Scope:** Azure Front Door Standard, synthetic Container Apps origin in South Africa North

**Status:** Testing complete for the instrumented origin. Native Blob control blocked by enforced security policy.

## Result

Front Door returned correct client-facing conditional responses for the ordinary ETag and date cases tested. The evidence does **not** support a blanket statement that Front Door ignores ETags or cannot return 304.

There are two important distinctions:

1. **Client validation is not origin forwarding.** On cold cache-enabled requests, the client validators were absent at the instrumented origin. The origin logged 200, but Front Door still returned 304 when the client's condition matched. With caching disabled, the validators reached the origin unchanged.
2. **A reproducible precedence discrepancy exists.** With caching enabled, a matching `If-None-Match` combined with an older `If-Modified-Since` returned 200 instead of the expected 304. The direct origin and caching-disabled control returned 304. Sending the matching ETag alone returned 304.

**Practical recommendation:** use `If-None-Match` alone when an ETag is available, retaining the ETag supplied for the selected representation. Do not add a date validator to that request. Escalate the paired-header discrepancy with the captured trace, rather than describing all Front Door conditional requests as unsupported.

This recommendation is bounded by the tested configuration. It is not a vendor support commitment or a validation of native Blob behaviour. Deployment identifiers and raw operational evidence have been omitted from this public report.

## Coverage

The accepted matrix contains **216 conditional observations**: nine conditions, cold and warm-path sequences, three repeats, and four configurations. Of these, **198 matched the fixture/HTTP expectation and 18 exhibited the same paired-header discrepancy**. All response-body checks passed, including zero-byte 304 responses and decoded gzip content hashes.

The first six conditions form the original 144-observation matrix. All 144 matched their expected client status. Additional conditions exposed the discrepancy that the original matrix missed.

| Configuration | Observations | Expected status observed | Paired-header discrepancies |
|---|---:|---:|---:|
| Cache on, compression off, identity | 54 | 48 | 6 |
| Cache off, compression off, identity | 54 | 54 | 0 |
| Cache on, compression on, identity | 54 | 48 | 6 |
| Cache on, compression on, gzip | 54 | 48 | 6 |
| Total | 216 | 198 | 18 |

The observations were collected on 5 October 2026. Separate paired-request, encoding-selection and TTL checks supplement this matrix.

For caching-disabled tests, "warm" means the same preparatory GET sequence was performed. It does not mean a cache entry existed. Every accepted caching-disabled conditional response reported `CONFIG_NOCACHE`.

### Client Outcomes

The cached outcomes below were consistent across compression off, compression on with identity, and compression on with gzip, on both cold and warmed paths.

| Request condition | Expected | Cache enabled | Cache disabled |
|---|---:|---:|---:|
| Matching strong ETag | 304 | 304 | 304 |
| Matching weak ETag | 304 | 304 | 304 |
| Non-matching ETag | 200 | 200 | 200 |
| `If-None-Match: *` | 304 | 304 | 304 |
| Matching modification date | 304 | 304 | 304 |
| Non-matching ETag + matching date | 200 | 200 | 200 |
| Older modification date alone | 200 | 200 | 200 |
| ETag list containing a matching weak tag | 304 | 304 | 304 |
| Matching ETag + older modification date | 304 | **200** | 304 |

The older-date checks used valid dates in 1970 and 2024, both earlier than the fixture's `Last-Modified: Wed, 01 Oct 2025 00:00:00 GMT`. The discrepancy is not confined to the Unix epoch date.

## Origin Correlation

The final accepted matrix has a positively correlated direct-baseline origin record for all 216 observations. Each record is joined by unique path and `X-Lab-Request-Id`, not by a cached response's `X-Lab-Origin-Id`.

| Accepted requests | Count | Instrumented-origin observation |
|---|---:|---|
| Cache-enabled cold conditionals | 81 | One correlated origin request each. Both client validator headers absent. Origin logged 200. |
| Cache-enabled warm conditionals | 81 | Each response reported `TCP_HIT` or `TCP_REMOTE_HIT`. No correlated conditional origin access in the collected logs. |
| Caching-disabled conditionals | 54 | One correlated origin request each. Sent validators preserved. Origin status matched the client response. |

On cache-enabled cold requests, Front Door added `Range: bytes=0-8388607`. The fixture intentionally ignores Range and returns the complete representation. With caching disabled, the observed Range header was absent.

The origin records its intended status and body length before writing the response. An origin log showing 200 and 8,029 bytes is not a packet-level measurement proving that the edge consumed every byte. The defensible conclusion is that the origin handled those requests without the client's validators, while the client-facing result still respected ordinary single-validator conditions.

Warm-hit observations support cache-tier conditional handling. They do not identify a particular POP/cache tier, and the absence of an origin record is qualified by the logging checks below.

### Cold-Request Trace

- Case: matching ETag, cold.
- Client sent the matching `If-None-Match` and received 304, zero bytes, `TCP_MISS`.
- The correlated origin request had no `If-None-Match` or `If-Modified-Since`, contained Range, and logged 200.

This is why a 304 alone does not prove forwarding, just as a 200 alone does not prove stripping.

## Precedence Discrepancy

[RFC 9110 section 13.1.3](https://httpwg.org/specs/rfc9110.html#field.if-modified-since) says a recipient **MUST ignore If-Modified-Since if the request contains If-None-Match**. The matching ETag should therefore determine these requests.

The unexpected cached 200 reproduced in **18 of 18** accepted matching-ETag/older-date cases, spanning three cache-enabled configurations and both cold and warm sequences. All **6 of 6** caching-disabled cases returned the expected 304. The supplemental direct-origin controls also returned 304.

To isolate the header effect from path selection or changing content, additional same-path sequences were run three times on both the baseline and gzip endpoints, and three times on the caching-disabled endpoint:

| Sequence on the same path | Cached endpoints, 6 sequences | Uncached endpoint, 3 sequences |
|---|---:|---:|
| Matching ETag alone | 304 | 304 |
| Same ETag + older date | **200** | 304 |
| Remove the date, keep the same ETag | 304 | 304 |
| Matching ETag + matching date | 304 | 304 |

All six cached responses in the problematic step were `TCP_HIT`. The body remained the correct representation. The observed consequence is an unnecessary full client response, not demonstrated stale-content delivery or data corruption.

Example for investigation:

```http
If-None-Match: "d02b3ef7c8a8d1c60c3c2154d215f1887e221756c631065f5dea09cc50eda860"
If-Modified-Since: Tue, 01 Oct 2024 00:00:00 GMT
```

The direct control returned 304. The corresponding warmed Front Door request returned 200, 8,029 bytes and `TCP_HIT`. Run identifiers and correlation headers are intentionally not published.

This is a reproducible discrepancy against the stated precedence rule. It has not been confirmed or explained by the Front Door service team.

## Compression and Revalidation

### Compression

- Unencoded fixture: 8,029 bytes with a strong ETag.
- Actual gzip responses: 75 bytes, with `Content-Encoding: gzip` and the ETag weakened to `W/"..."`.
- Bounded decompression produced exactly 8,029 bytes and the same SHA-256 as the direct identity representation.
- Matching strong and weak client validators both produced 304 in the ordinary cases. This is consistent with weak comparison for `If-None-Match`, not proof of encoded byte equality.
- Three additional runs used the **edge-returned weak ETag** and each returned 304.
- Alternating gzip, identity, then gzip on a single path returned the appropriate representation and validator each time. Identity returned the original strong ETag and full body; gzip returned the weak ETag and compressed body.

### TTL Expiry

Two separate paths distinguish unconditional-first from conditional-first behaviour after waiting 130 seconds beyond a verified cache hit, exceeding the origin's 120-second TTL:

1. **Unconditional first:** client sent no validator. Origin received both ETag and date validators and logged 304. Client received 200 with `TCP_REVALIDATED_HIT`. A subsequent matching client validator returned 304 with `TCP_HIT`.
2. **Conditional first on a different stale path:** client sent matching `If-None-Match`. Origin received ETag and date validators and logged 304. Client received 304 with `TCP_REVALIDATED_HIT`.

The first sequence directly demonstrates Front Door's own origin revalidation independently of client-supplied validators. These are unchanged-content tests, not changed-content freshness tests.

## Evidence Quality and Exclusions

- Synthetic data only, one Container App replica and one image digest throughout the accepted tests.
- Unique path per condition/state/run. Validators obtained directly from ACA before the first edge request, without warming the cold edge path.
- Stable, separately configured endpoints used the same Front Door profile and origin group. Their configuration differed only as required for the cache/compression controls.
- An attempted same-route cache-disable experiment contained mixed `CONFIG_NOCACHE`, `TCP_MISS` and hit responses during propagation. Its 36 observations are **excluded** from the 216 accepted observations. Readiness canaries and startup 404s are also excluded.
- Actual response cache and encoding headers are retained. A preceding warm-up hit is never treated as proof that the next request hit the same cache.
- Persistent logs were queried through the authenticated workspace ARM API, including its query-status metadata.
- Query completion metadata was checked. Every accepted direct baseline and every accepted uncached conditional has a correlated record. End-of-study sentinel requests were also checked after ingestion. These are completeness checks, not an absolute guarantee of lossless logging.
- One ingested row contained two adjacent complete JSON objects from concurrent fixture prints, followed by a blank row. The strict JSON-stream decoder preserves both records, ignores only whitespace and rejects malformed/truncated content. Raw rows are retained, and this handling has a regression test.
- System logs recorded one readiness-probe timeout during the parallel matrix. The final revision remained healthy and unchanged. No client error responses or invalid bodies occurred in the accepted matrix. This transient warning is retained in the evidence.
- No production endpoints, alternative geography, other SKU or service support contract was tested.

## Blob Control: Not Executed

The attempted native Blob control was blocked by environment security policy requiring private access. The attempted anonymous fixture container returned `PublicAccessNotPermitted`.

No policy exception was used. The uncompleted Blob deployment and write paths are not part of the public harness.

Consequently, **this report does not establish native Blob ETag/range behaviour through Front Door**, nor mutable-object freshness. Completing that control requires an approved private-access/authentication topology and may require a different Front Door SKU/configuration. That is a separate experiment, not a result to invent from the synthetic origin.

## Reproduce and Audit

Code:

- `src/frontdoor_lab/probe.py`: original six-condition cold/warm matrix, raw-byte hashing and explicit bounded gzip validation.
- `src/frontdoor_lab/experiments.py`: supplemental conditions, paired-header checks, encoding selection and independent TTL sequences.
- `src/frontdoor_lab/analysis.py`: strict log parsing and path/request-ID correlation. It does not infer log completeness automatically.
- `infra/test-endpoints.bicep`: parameterised fixed caching-disabled and compression-enabled controls.
- `infra/route-control.bicep`: explicit route-only configuration changes.

Run the local validation:

```bash
PYTHONPATH=src python3 -B -m unittest discover -s tests -p 'test_*.py' -v
```

After installing the package, set your own approved HTTPS base URLs and reproduce the paired-header observation with fresh paths:

```bash
frontdoor-experiments precedence-pair \
  --origin "$LAB_ORIGIN" \
  --edge "$LAB_EDGE" \
  --label 'Paired ETag/date reproduction' \
  --old-date 'Tue, 01 Oct 2024 00:00:00 GMT' \
  --repeats 3 --confirm-lab
```

This report publishes aggregate findings and a reproducible harness, not raw request traces or deployment records. Keep new evidence private under `evidence/` and review it separately before sharing. The absence of the original raw dataset limits independent audit of this report; a new run must stand on its own recorded configuration and observations.
